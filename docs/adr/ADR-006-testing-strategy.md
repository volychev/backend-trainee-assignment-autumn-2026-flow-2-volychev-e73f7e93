# ADR-006: Стратегия тестирования

**Дата:** 2026-09-07  
**Статус:** Принято  
**Участники:** Senior Backend Engineer, QA Engineer

---

## Контекст

Проект достиг стадии, когда все ключевые сервисы реализованы. Перед финальной сдачей необходимо зафиксировать стратегию проверки корректности поведения системы и настроить инфраструктуру тестирования.

Требования к тестированию:
- Тесты должны покрывать реальное взаимодействие с HTTP-слоем и базой данных.
- Каждый тест должен быть изолирован — не оставлять данных в БД после завершения.
- Тесты должны запускаться как локально, так и внутри Docker-контейнера.

---

## Решение

### Уровень тестирования

Для MVP принято решение сосредоточиться на **интеграционных тестах** уровня HTTP-эндпоинта. Юнит-тесты бизнес-логики и E2E-тесты (с реальным межсервисным взаимодействием) выходят за рамки текущего этапа.

### Инструменты

| Инструмент | Роль |
|---|---|
| `pytest` + `pytest-asyncio` | Запуск асинхронных тестов |
| `httpx.AsyncClient` + `ASGITransport` | In-process HTTP-клиент без реального сетевого вызова |
| SQLAlchemy async session | Изолированная тестовая сессия с rollback после каждого теста |

### Изоляция тестов

Каждый тест выполняется в изолированном контексте:
- Фикстура `clean_db` очищает таблицы (`TRUNCATE CASCADE`) перед каждым тестом.
- `AsyncSession` создаётся с `NullPool`, чтобы избежать проблем с привязкой asyncpg-соединений к прерванным event loop.
- Каждая попытка записи или вызова API выполняется в чистом состоянии БД. Это гарантирует полной изоляцию тестов и детерминированность результатов.


### Dependency override

FastAPI-зависимость `get_db` переопределяется через `app.dependency_overrides` на тестовую сессию. Это позволяет тестировать полный стек (роутер → сервис → БД) без изменения production-кода.

### Покрытие

| Файл | Эндпоинт | Сценарий |
|---|---|---|
| `test_restaurants.py` | `GET /restaurants` | Возвращает список активных ресторанов |
| `test_menu.py` | `GET /restaurants/{id}/menu` | Возвращает доступные позиции меню |
| `test_orders.py` | `POST /orders`, `GET /orders/{id}` | Создание заказа, расчёт суммы, статус PENDING |
| `test_webhooks.py` | `PATCH /orders/{id}/status` | Обновление статуса заказа от ресторана |

---

## Последствия

**Положительные:**
- Тесты изолированы и воспроизводимы.
- Не требуется отдельная тестовая БД — используется та же БД с откатом транзакций.
- Легко расширить покрытие без изменения архитектуры тестирования.

**Отрицательные:**
- Вебхук в `POST /orders` упадёт с `httpx.RequestError` в тестовой среде (Mock API не запущен), но это ожидаемо и обработано в коде.
- Юнит-тесты сервисного слоя не реализованы в рамках MVP.
