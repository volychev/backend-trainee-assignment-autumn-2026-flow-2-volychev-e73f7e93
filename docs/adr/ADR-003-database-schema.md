# ADR-003: Разработка схемы базы данных

**Дата:** 2026-09-07  
**Статус:** Принято  
**Участники:** Team Lead, Backend Engineer

---

## Контекст

Необходимо спроектировать реляционную схему данных для MVP «Авито.Кухня».  
Требования к схеме:
- Поддержка основных сущностей: рестораны, меню, заказы, позиции заказа
- Возможность масштабирования: добавление новых сущностей без дорогостоящих миграций
- Сохранение исторических данных (цена в момент заказа не должна меняться при изменении меню)
- Корректное связывание пользователей и заказов без сервиса авторизации

---

## Решение

### Выбор типа данных для первичных ключей

Выбраны **UUID** вместо `SERIAL` (автоинкрементные integer).

**Обоснование:**
- UUID не раскрывают количество записей в системе (безопасность)
- UUID не создают конкуренцию за последовательность при горизонтальном масштабировании
- UUID удобны при будущей миграции на микросервисы (нет коллизий между сервисами)
- PostgreSQL 16 предоставляет встроенную функцию `gen_random_uuid()`

### Выбор типа для цен

Выбран `NUMERIC(10,2)` вместо `FLOAT` или `INTEGER (копейки)`.

**Обоснование:**
- `FLOAT` имеет проблемы с точностью (0.1 + 0.2 != 0.3) — критично для денег
- `NUMERIC` обеспечивает точную арифметику для финансовых операций
- `(10,2)` — до 99 999 999.99 рублей, достаточно для любого меню

### Снимок цены в `order_items.unit_price`

Поле `unit_price` в таблице `order_items` **дублирует** цену из `menu_items.price`.

**Обоснование:**
- Если ресторан изменит цену блюда, старые заказы должны сохранить исходную цену
- Это стандартная практика (Order Snapshot Pattern) в e-commerce
- Позволяет корректно пересчитывать итоги и строить аналитику

### Хранение `user_id` в заказах

В MVP нет сервиса авторизации, поэтому `orders.user_id` хранит UUID из заголовка `X-User-ID`.

**Обоснование:**
- Позволяет связать заказы с пользователем без внешнего FK
- При появлении сервиса авторизации — `user_id` уже есть в схеме, добавится только внешний ключ

### Статусы заказа

Статус хранится как `VARCHAR(20)`, а не как отдельная таблица-справочник.

**Допустимые значения:**
```
PENDING -> CONFIRMED -> COOKING -> READY -> DELIVERED
                                 |
                                 v
                             CANCELLED
```

**Обоснование:**
- На MVP статусы стабильны, отдельная таблица избыточна
- Валидация статусов на уровне Pydantic enum
- При необходимости легко заменить на PostgreSQL native `ENUM` type

### Индексы

Запланированные индексы для производительности:

| Таблица | Поле | Тип | Причина |
|---|---|---|---|
| `menu_items` | `restaurant_id` | B-tree | Частый запрос меню по ресторану |
| `orders` | `user_id` | B-tree | Запрос истории заказов пользователя |
| `orders` | `restaurant_id` | B-tree | Запрос заказов ресторана |
| `orders` | `status` | B-tree | Фильтрация по статусу |
| `order_items` | `order_id` | B-tree | Загрузка позиций заказа |

## Последствия

### Положительные

- **Историческая корректность**: цены в заказах не изменяются ретроспективно
- **Масштабируемость схемы**: UUID PK позволяют добавлять сервисы без коллизий
- **Простота миграций**: Alembic автоматически генерирует diff между моделями SQLAlchemy и текущей схемой
- **Нормализация**: данные не дублируются (кроме намеренного снимка цены)

### Отрицательные / Риски

- **Нет каскадных операций**: при удалении ресторана вручную нужно обработать связанные данные
  - *Митигация*: мягкое удаление через `is_active = FALSE`, физическое удаление не допускается
- **UUID медленнее integer** для индексов (случайная вставка вызывает фрагментацию B-tree)
  - *Митигация*: использование `gen_random_uuid()` с UUIDv4; при необходимости — переход на UUIDv7 (монотонный)
- **VARCHAR для статуса**: отсутствие DB-level ограничений на допустимые значения
  - *Митигация*: проверка на уровне Pydantic enum в приложении; миграция на PostgreSQL `ENUM` при стабилизации
