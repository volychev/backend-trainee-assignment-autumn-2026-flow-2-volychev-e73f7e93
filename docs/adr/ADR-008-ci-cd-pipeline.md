# ADR-008: Настройка CI/CD пайплайна

**Дата:** 2026-09-07  
**Статус:** Принято  
**Участники:** DevOps Engineer, Senior Backend Engineer

---

## Контекст

С завершением разработки MVP платформы "Авито.Кухня", возникает необходимость в автоматизированной проверке качества кода и работоспособности тестов перед каждым слиянием кода. Это поможет избежать регрессий и поддерживать стандарты кодовой базы. 
Нужно выбрать платформу для CI и определить основные шаги проверок. Поскольку MVP не требует сложного деплоя в production (на данном этапе), пайплайн будет ограничен Continuous Integration (CI).

## Решение

В качестве CI-платформы выбран **GitHub Actions**, так как он встроен в репозиторий, не требует дополнительной инфраструктуры и имеет богатую экосистему готовых `actions`.

Пайплайн настроен на запуск при событиях `push` и `pull_request` в ветки `main` и `master`. 

Процесс разделен на 3 параллельные задачи (jobs):

1. **Lint and Typecheck (`lint-and-typecheck`)**
   - Устанавливает Python 3.13 и Poetry.
   - Проверяет код линтером `ruff` (включая форматирование).
   - Проверяет статическую типизацию с помощью `mypy`.
   - Это самый быстрый шаг, который сразу отклоняет код, не соответствующий стандартам.

2. **Run Integration Tests (`test`)**
   - Поднимает временную (ephemeral) базу данных PostgreSQL (16-alpine) через `services`.
   - Устанавливает зависимости.
   - Применяет миграции базы данных Alembic на поднятом PostgreSQL (`alembic upgrade head`).
   - Запускает интеграционные тесты `pytest`, передавая `TEST_DATABASE_URL` на ephemeral базу данных (с использованием порта `5432` на `localhost` виртуальной машины runner'а).

3. **Docker Build Check (`build-check`)**
   - Проверяет процесс сборки Docker-образов для Main API и Mock Restaurant API.
   - Гарантирует, что конфигурация `Dockerfile` корректна и приложение успешно упаковывается в контейнер без ошибок. 
   - Образы не пушатся в registry, только проверяется сам билд.

## Последствия

**Положительные:**
- Автоматическая гарантия того, что в `main` не попадёт сломанный код, код с ошибками типизации или неформатированный код.
- Тесты прогоняются в чистом окружении на свежей базе данных, имитируя реальные условия запуска.
- Инфраструктура в виде кода (конфигурация лежит в репозитории).

**Отрицательные:**
- Время выполнения CI занимает ресурсы и несколько минут на каждый коммит/PR (установка Python, скачивание Docker-образов). В будущем может потребоваться настройка кэширования зависимостей Poetry и слоёв Docker.
