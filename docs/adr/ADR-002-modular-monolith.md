# ADR-002: Выбор архитектуры модульного монолита

**Дата:** 2026-09-07  
**Статус:** Принято  
**Участники:** Team Lead, System Architect

---

## Контекст

Необходимо выбрать архитектурный стиль для Main API «Авито.Кухня» (MVP).  
Рассматривались три варианта:

1. **Монолит** (единый модуль без явных границ)
2. **Модульный монолит** (единый процесс с явными границами модулей)
3. **Микросервисы** (отдельные процессы/деплойменты)

Контекст принятия решения:
- Стадия **MVP** — неизвестны реальные пользовательские сценарии и нагрузки
- **Малая команда** (1–2 backend-разработчика на старте)
- Требуется **быстрый старт** и итерация
- Доменная модель пока **простая**: restaurants, menu_items, orders, order_items
- После MVP планируется **масштабирование** — архитектура должна это допускать

---

## Решение

Выбран **модульный монолит** (Modular Monolith).

Приложение запускается как **единый процесс** (один `uvicorn`-сервер), но код организован в **независимые модули** с чёткими границами:

```
app/
 restaurants/   # Bounded Context: заведения
 menu_items/    # Bounded Context: позиции меню
 orders/        # Bounded Context: заказы
 order_items/   # Bounded Context: позиции заказа
 core/          # Shared: конфигурация, БД
```

### Правила взаимодействия модулей

- Модули общаются через **явные вызовы сервисов** (не через прямой доступ к моделям других модулей)
- Межмодульные зависимости **направлены**: `orders` использует `menu_items`, но не наоборот
- Общая БД разделена **логически** (каждый модуль владеет своими таблицами)
- Нет паттернов DDD (Repository, Unit of Work) — избыточны для MVP

### Сравнение вариантов

| Критерий | Монолит | Модульный монолит | Микросервисы |
|---|---|---|---|
| Скорость старта |  Высокая |  Высокая |  Низкая |
| Поддерживаемость |  Низкая |  Высокая |  Высокая |
| Масштабируемость |  Сложно |  Ограничена |  Высокая |
| Сложность инфраструктуры |  Минимальная |  Минимальная |  Высокая |
| Путь к микросервисам |  Сложный рефакторинг |  Естественная декомпозиция | — |
| Операционные расходы |  Низкие |  Низкие |  Высокие |

---

## Последствия

### Положительные

- **Простота развёртывания**: один Docker-образ, один сервис в Compose
- **Нет сетевых задержек** между модулями (вызовы внутри процесса)
- **Единая транзакция** при работе с несколькими модулями (например, создание заказа и его позиций)
- **Путь к микросервисам**: модули с чёткими границами легко вынести в отдельные сервисы при необходимости — достаточно заменить прямые вызовы на HTTP/gRPC
- **Нет overhead**: не нужен service mesh, API Gateway, distributed tracing на MVP

### Отрицательные / Риски

- **Единая точка отказа**: падение одного модуля роняет весь сервис
  - *Митигация*: мониторинг + health checks + автоперезапуск через Docker
- **Горизонтальное масштабирование**: масштабируется весь монолит, а не отдельные модули
  - *Митигация*: на MVP нагрузка не предполагает этой проблемы; при необходимости — декомпозиция на микросервисы
- **Риск нарушения границ**: разработчики могут «срезать путь» и обращаться к моделям других модулей напрямую
  - *Митигация*: код-ревью + явно описанные правила взаимодействия в документации
