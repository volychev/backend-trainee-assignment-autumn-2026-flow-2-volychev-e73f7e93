# ADR-004: Использование HTTP Webhooks вместо брокера сообщений

**Дата:** 2026-09-07  
**Статус:** Принято  
**Участники:** Team Lead, System Architect

---

## Контекст

Необходимо выбрать механизм передачи событий между Main API и сервисом ресторана (Mock Restaurant API).  
Ключевое событие: **«Создан новый заказ»** → ресторан должен получить уведомление и подтвердить/отклонить его.

Рассматривались варианты:

1. **HTTP Webhooks** (синхронный вызов из Main API в ресторан)
2. **Брокер сообщений** (Kafka, RabbitMQ, Redis Pub/Sub)
3. **Polling** (ресторан сам периодически запрашивает новые заказы)

---

## Решение

Выбраны **HTTP Webhooks** для передачи уведомлений о заказах.

### Схема взаимодействия

```
Клиент
  |
  | POST /orders
  v
Main API
  | 1. Сохраняет заказ в БД (статус PENDING)
  | 2. Асинхронно отправляет вебхук
  v
Mock Restaurant API (POST /webhook/order)
  | Проверяет наличие позиций
  | Обновляет статус через Main API
  v
Main API (PATCH /orders/{id}/status)
  | Обновляет статус в БД
```

### Почему не брокер сообщений

| Критерий | Webhooks | Kafka/RabbitMQ |
|---|---|---|
| Сложность настройки |  Нулевая (HTTP) |  Высокая (отдельный сервис) |
| Инфраструктурные расходы |  Нет |  Доп. контейнер, ресурсы |
| Гарантия доставки |  Best-effort |  At-least-once / Exactly-once |
| Обработка сбоев |  Требует retry-логики |  Встроенная retry + DLQ |
| Масштабируемость |  Ограничена |  Высокая |
| Время старта MVP |  Минимальное |  Значительное |
| Наблюдаемость |  Логи HTTP |  Требует Kafka UI |

### Почему не polling

- Неэффективен: избыточные запросы при низкой нагрузке
- Задержка между созданием заказа и его обработкой рестораном зависит от интервала опроса
- Сложнее масштабировать при большом числе ресторанов

### Обработка отказов при вебхуках

Для MVP реализована простая логика:

1. Main API отправляет вебхук **один раз** при создании заказа
2. При недоступности ресторана — заказ остаётся в статусе `PENDING`
3. Ресторан может впоследствии самостоятельно запросить список PENDING-заказов

**Retry-логика** (для будущего):
- Exponential backoff: 1s → 5s → 30s → 5min
- Dead Letter Queue при исчерпании попыток
- Статус заказа → `CANCELLED` при невозможности уведомления

---

## Последствия

### Положительные

- **Нулевые инфраструктурные расходы**: не нужен Kafka, RabbitMQ, Redis
- **Docker Compose** остаётся простым: `postgres + main-api + mock-restaurant`
- **Отладка**: HTTP-запросы легко логировать, трассировать и воспроизводить
- **Скорость разработки**: не нужно изучать клиентские библиотеки брокеров

### Отрицательные / Риски

- **Нет гарантии доставки**: если ресторан недоступен в момент заказа — вебхук потеряется
  - *Митигация*: на MVP допустимо; при production — добавить retry + outbox pattern
- **Синхронная зависимость**: Main API напрямую зависит от доступности ресторана
  - *Митигация*: timeout на HTTP-вызов (5s), асинхронная отправка (не блокирует ответ клиенту)
- **Масштабирование**: при 1000+ ресторанах вебхуки создают нагрузку на Main API
  - *Митигация*: при масштабировании — замена на Kafka или другой брокер (ADR подлежит пересмотру)
