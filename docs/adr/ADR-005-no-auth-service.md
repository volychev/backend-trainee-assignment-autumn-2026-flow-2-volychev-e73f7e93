# ADR-005: Отказ от сервиса авторизации — доверие заголовку X-User-ID

**Дата:** 2026-09-07  
**Статус:** Принято  
**Участники:** Team Lead, System Architect

---

## Контекст

В типичном production-приложении требуются:
- **Аутентификация**: «Кто ты?» (проверка личности через JWT/OAuth2/session)
- **Авторизация**: «Что тебе можно?» (проверка прав доступа к ресурсам)

Для MVP «Авито.Кухня» явно указано в ТЗ:
> «Авторизацию и аутентификацию пользователей реализовывать, как и клиентскую часть, не нужно»

Тем не менее, API должен знать, **от какого пользователя** поступает запрос, чтобы:
- Связать заказ с пользователем (`orders.user_id`)
- В будущем — фильтровать историю заказов по пользователю

Рассматривались варианты:
1. Полностью анонимные запросы (без идентификации пользователя)
2. JWT-авторизация (полноценный auth-сервис)
3. Доверенный заголовок `X-User-ID`

---

## Решение

Выбрана стратегия **доверенного заголовка `X-User-ID`**.

### Механизм работы

```
Клиент                Main API
  |                      |
  | GET /orders          |
  | X-User-ID: <uuid>    |
  |--------------------> |
  |                      | Читает X-User-ID как user_id
  |                      | Создаёт / фильтрует заказы
  | <=================== |
```

**Реализация в FastAPI:**

```python
# app/core/dependencies.py
from uuid import UUID
from fastapi import Header, HTTPException

async def get_current_user_id(
    x_user_id: UUID | None = Header(default=None)
) -> UUID:
    if x_user_id is None:
        raise HTTPException(status_code=400, detail="X-User-ID header is required")
    return x_user_id
```

Заголовок **обязателен** для endpoint'ов, работающих с данными пользователя (создание заказа, история заказов). Для публичных endpoint'ов (список ресторанов, меню) — заголовок не требуется.

### Почему не полноценный auth-сервис

| Критерий | X-User-ID | JWT / OAuth2 |
|---|---|---|
| Время реализации | ✅ < 1 часа | ❌ Дни |
| Сложность | ✅ Минимальная | ❌ Высокая |
| Безопасность | ❌ Нет верификации | ✅ Криптографически верифицирован |
| Соответствие ТЗ | ✅ Явно разрешено | ⚠️ Избыточно для MVP |
| Путь к production | ✅ Заменить один middleware | ✅ Независимый сервис |

### Почему не полностью анонимные запросы

- Без `user_id` невозможно связать заказ с пользователем
- История заказов не может быть персонализирована
- Закладывает техдолг, который дорого исправлять при появлении авторизации

## Последствия

### Положительные

- **Скорость MVP**: авторизация не блокирует разработку основных сценариев
- **Фокус на бизнес-логике**: заказы, меню, вебхуки
- **Правильная архитектура**: `user_id` присутствует в данных, легко добавить настоящую авторизацию
- **Тестируемость**: легко передавать произвольный UUID в тестах без мока auth-сервиса

### Отрицательные / Риски

- **Безопасность**: любой клиент может притвориться любым пользователем
  - *Митигация*: MVP запускается в закрытой среде; доступ через Авито-инфраструктуру, которая подставляет реальный `X-User-ID` на API Gateway уровне
- **Нет авторизации действий**: пользователь A теоретически может видеть заказы пользователя B, зная его UUID
  - *Митигация*: добавить проверку `order.user_id == current_user_id` при чтении конкретного заказа
- **Технический долг**: перед production ОБЯЗАТЕЛЬНО добавить JWT + auth middleware
  - *Митигация*: добавление auth является одним изолированным изменением — замена `get_current_user_id` dependency на JWT-верификатор

### Путь к production

При масштабировании:
1. Добавить **API Gateway** (nginx / Kong), который верифицирует JWT и проксирует `X-User-ID`
2. Заменить `get_current_user_id` dependency на JWT-декодирование
3. Данные в БД (`orders.user_id`) не меняются — миграция не нужна
